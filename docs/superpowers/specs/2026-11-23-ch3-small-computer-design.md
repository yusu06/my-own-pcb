# 3장 "작은 컴퓨터" 설계

상위 설계: `docs/superpowers/specs/2026-11-21-hw-study-tool-design.md` (§5 커리큘럼, §5.1 과제 유형 원칙). 이 문서는 그중 3장만 정한다.

## 1. 의도

3장은 **가벼운 다리**다. 2장까지 만든 부품(레지스터, 카운터, MUX, 가산기, FSM)이 모이면 CPU가 된다는 것을 보여 주고, 5장(MCU와 펌웨어)에서 "MCU = 이 CPU + 메모리 + 주변장치를 한 칩에", "펌웨어 = 3-6에서 ROM에 넣은 그 프로그램"을 바로 알아보게 하는 것이 목표다.

성공 기준: 3장을 마친 학습자가 "명령어를 꺼내고(fetch) → 해석하고(decode) → 실행한다(execute)"는 한 바퀴를 자기 말로 설명할 수 있고, 4비트 CPU에서 짧은 프로그램을 한 번 직접 돌려 봤다.

## 2. 목표 / 비목표 / 반목표

- **목표**: 7단원(설계 문서 순서 그대로), 모두 기존 과제 형식(Verilog 조합·순차, 퀴즈)으로 만든다. 3장 전체에서 **명령어 집합 하나**를 공유해 단원이 쌓여 CPU가 된다.
- **비목표**: 해석기에 메모리 배열(`reg [3:0] mem [0:15]`) 추가, 어셈블리 편집기·어셈블러, 새 과제 종류, 3장용 그리기(블록 조립) 과제, 파이프라인·인터럽트·스택 같은 실제 CPU 기능.
- **반목표**(기술적으로 돌아가도 실패): 3장이 2장보다 길고 무거워지는 것(단원당 과제 1~2개, `minutes` 20 이하 — 콘텐츠 테스트 상한), CPU 전체를 처음부터 쓰게 해서 막히는 것, 5장과 이어지지 않고 따로 노는 것.

## 3. 제약

- 기존 해석기 부분집합 안에서만 쓴다. 스파이크로 확인한 것: 모듈 여러 개 + 인스턴스, `output reg`, `wire x = 식;`, `case`(라벨 여러 개 `4'd0, 4'd1:`), 16진 리터럴, `always @(*)` 안의 `case` ROM. 장난감 CPU(ROM·ALU·PC·A 레지스터) 60클럭이 약 3 ms에 돌았고 상한(인스턴스 2000, 블록 3000)과 거리가 멀다.
- 배열이 없으므로 메모리는 **ROM = `case`**, **RAM = 레지스터 여러 개**로 쓴다. 개념 카드에서 "실제 Verilog는 배열로 쓰지만 이 앱에서는 풀어 쓴다"고 솔직히 말한다.
- 배포된 id는 바꾸지 않는다. 3장 단원 id는 `3-1` ~ `3-7`, 파일은 `src/lessons/ch3/3-N-<이름>.ts`, `LESSONS` 끝에 순서대로 붙인다.
- 공개 저장소이므로 콘텐츠·문서에 개인정보를 넣지 않는다(기존 규칙 그대로).

## 4. 접근 방식

| 안 | 내용 | 장단점 | 결과 |
|---|---|---|---|
| A. 7단원 유지, 과제는 가볍게 | 기존 과제 형식만 사용. ROM은 `case`, CPU는 거의 다 준 뼈대에서 한 조각만 채움, 로봇 프로그램은 ROM `case` 줄 채우기 | 새 엔진 작업이 거의 없음. 기계어를 숫자로 적는 게 조금 딱딱함(→ 명령어 이름 `localparam`으로 완화) | **채택** |
| B. 3~4단원으로 축소 | ALU+해독기 → PC+ROM → CPU 관찰 → 왜 MCU | 가장 빠르지만 설계 문서 흐름이 깨지고 손으로 해 볼 것이 줄어듦 | 탈락 |
| C. 어셈블리 편집기 추가 | 로봇 단원에서 `LDI 3` 같은 글을 쓰면 내장 CPU가 실행 | 가장 재미있지만 새 과제 종류·채점기가 필요해 "가벼움"과 어긋남 | 탈락 |

사용자가 A를 골랐다.

## 5. 공유 명령어 집합 "토이4"

모든 3장 단원이 같은 것을 쓴다. 명령어는 8비트 `{op[3:0], n[3:0]}`, 레지스터는 누산기 A(4비트) 하나, 출력 포트 OUT(4비트), 입력 포트 SENSOR(4비트), 프로그램 카운터 PC(4비트, ROM 16칸).

| op | 이름 | 동작 | PC |
|---|---|---|---|
| 0 | `LDI n` | A ← n | +1 |
| 1 | `ADD n` | A ← A + n (4비트, 넘치면 버림) | +1 |
| 2 | `SUB n` | A ← A − n (4비트) | +1 |
| 3 | `OUT` | OUT ← A | +1 |
| 4 | `JMP n` | — | ← n |
| 5 | `JZ n` | — | A == 0이면 ← n, 아니면 +1 |
| 6 | `IN` | A ← SENSOR | +1 |
| 7~15 | `HLT` | 아무것도 안 함 | 그대로(멈춤) |

- rst = 1인 클럭 에지에 PC, A, OUT이 0이 된다.
- 뼈대 코드에는 `localparam LDI = 4'd0, ADD = 4'd1, …;`을 넣어 두고 ROM 줄을 `4'd0: data = {IN, 4'd0};`처럼 이름으로 쓰게 한다(기계어 숫자 대신).
- TS 쪽 기준 모델은 `src/lessons/ch3/toy4.ts` 하나에 둔다: 명령어 표(퀴즈·카드에서도 씀)와 `toy4(program: number[])`가 돌려주는 `SeqSpec.model` 호환 상태 모델(입력 `{clk, rst, sensor}` → 출력 `{out, pc}`). 해석기와 따로 TS로 쓰는 기존 원칙(해석기 버그가 모범 답안과 같이 숨지 않게)을 따른다.

## 6. 단원

모든 단원은 기존처럼 의뢰서 → 개념 카드 → 과제 → 실제 기기에서는 → 퀴즈 2~3문제. 순차 과제는 기존 규칙대로 `clocked()` 각본과 `from: 1`(리셋 전 단계는 채점하지 않음)을 쓴다.

| id | 제목(가) | 의뢰 예 | 과제 |
|---|---|---|---|
| 3-1 | 메모리 | 오르골 멜로디 표 / 사물함 4칸 | ① 조합: 4비트 주소 → 8비트 값 ROM을 `case`로(멜로디 음표 표 같은 의뢰). ② 순차: 4칸 RAM(주소 2비트, `we`, 쓰기는 클럭, 읽기는 바로) — 레지스터 4개로 |
| 3-2 | ALU | 계산기 칩 하나로 여러 연산 | 조합: `a`, `b`(4비트), `op`(2비트: 통과 b / 더하기 / 빼기 / 통과 a) → `y`, `zero`. 1-10 가산기·1-8 MUX를 다시 쓰는 것이라고 카드에서 이음 |
| 3-3 | 명령어 | 리모컨 신호표 읽기처럼 "숫자가 곧 명령" | 조합: 8비트 명령어 → 제어 신호(`alu_op`, `use_sensor`, `write_a`, `write_out`, `jump`, `jz`). 토이4 표를 그대로 구현 |
| 3-4 | 프로그램 카운터 | 오르골 넘김 장치: 한 칸씩, 필요하면 점프 | 순차: `rst`, `load`, `d[3:0]` → `pc`(load면 d, 아니면 +1). 2-6 카운터를 고치는 것 |
| 3-5 | 4비트 CPU | 장난감 회사: "칩 하나로 여러 장난감" | 순차: ROM·ALU·PC·A가 다 연결된 CPU 뼈대에서 **실행부 `case (op)` 한 덩어리만** 채운다. ROM에는 고정 프로그램(예: 3부터 거꾸로 세며 OUT). 채점 = `toy4(그 프로그램)` 모델과 클럭마다 `out`, `pc` 비교 |
| 3-6 | 장난감 로봇 프로그램 | 장애물 피하는 로봇 | 순차: 완성된 CPU는 그대로 두고 **ROM `case` 줄만** 채워 프로그램을 쓴다(예: 센서 0이면 OUT=3 직진, 1이면 OUT=1 회전). 채점은 아래 "관찰 지점" 방식 |
| 3-7 | 왜 MCU인가 | (의뢰 없이 정리하는 단원도 가능, 형식은 유지) | 과제 없음(`tasks: []`, 2-2와 같음). 카드 + 퀴즈만. 내용: CPU만으로는 아무것도 못 한다 → 메모리·입출력(GPIO)·타이머·ADC를 한 칩에 = MCU. 3-6의 ROM 프로그램 = 펌웨어. 5장에서는 기계어 대신 C로 쓴다 |

### 3-6 채점: 관찰 지점

학습자 프로그램마다 명령어 수와 타이밍이 달라서 클럭마다 정답을 정할 수 없다. 그래서 센서 값을 일정 클럭(예: 16클럭) 동안 유지하는 구간을 여러 개 두고, **각 구간 마지막 몇 클럭에서만** `out`을 검사한다(그 사이는 "상관없음").

- 필요한 작은 변경: 순차 채점에서 모델이 어떤 출력 값을 `undefined`로 돌려주면 그 칸은 채점하지 않는다(`grader/verilog.ts`의 `bad` 계산). 타임라인에는 그 칸을 회색·"상관없음"으로 보여 준다(`ui/timeline.ts`, 지금은 `기대 undefined`가 뜰 것).
- 구간 길이는 모범 답안의 한 바퀴보다 넉넉하게 잡고, 의뢰서에 "센서가 바뀌고 N클럭 안에 반응하면 된다"고 적는다.

### 각 단원의 "실제 기기에서는"(방향만)

3-1: 실제 칩의 플래시(ROM)·SRAM, 크기 단위. 3-2: 실제 ALU는 플래그(자리올림, 음수)를 더 낸다. 3-3: 실제 명령어 집합(예: ARM, RISC-V)도 같은 원리, 길이만 다르다. 3-4: 전원이 들어오면 PC가 정해진 주소(리셋 벡터)에서 시작한다. 3-5: 실제 CPU는 이 한 바퀴를 수십억 번/초 돌린다. 3-6: 로봇 장난감·가전 속 펌웨어. 3-7: 5장 예고.

## 8. Claude가 정한 것(검토 바람)

- 명령어 집합 토이4(위 표). 레지스터는 A 하나, OUT·SENSOR 4비트.
- 3-5는 실행부만 채우기, 3-6은 ROM 줄만 채우기. 학습자가 CPU 코드를 고쳐 "답만 내는" 꼼수는 막지 않는다(혼자 공부하는 앱이라 이득이 없음).

- 3장 해금·진행은 기존 단원과 같은 규칙(따로 손대지 않음).

## 9. 빌더에게 맡기는 것

- 의뢰인·제목·카드 문장, 퀴즈 문항, 용어집 항목(`memory`, `address`, `rom`, `ram`, `alu`, `instruction`, `opcode`, `pc`, `cpu`, `mcu`, `firmware` 등)의 정확한 문구.
- 3-5 고정 프로그램과 3-6 센서 각본·구간 길이의 구체 값.
- 각 과제의 오답(`wrong`) 2~3개: 흔한 실수(JZ 조건 뒤집기, PC +1 빼먹기, ADD/SUB 바꾸기, ROM 주소 하나 밀기 등).
- 3-1 RAM 읽기를 조합으로 둘지, 3-1 의뢰 소재를 무엇으로 할지.
- 기존 콘텐츠 테스트(`src/lessons/content.test.ts`)가 3장에도 그대로 적용되는지 확인하고, 필요하면 "관찰 지점" 규칙 테스트를 더한다.
